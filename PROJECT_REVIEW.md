# Свод ревью проекта pcb-design-review

В репозитории есть переносимая методика ревью, черновой каталог из 181 правила в 20 семействах, шесть стартовых профилей, JSON Schema и пример отчёта. Методика различает функциональные проблемы, электробезопасность, эмиссию, устойчивость и ПЭМИН. Исходные данные конкретной платы в репозитории отсутствуют. Ниже приведены замечания к инструменту и его данным.

## Что было исправлено

- Профили ранее служили шаблонами. Локальный CLI теперь учитывает наследование, отбирает правила по признакам и объясняет неопределённую применимость и исключения.
- Числа в схеме профиля можно было указать без прослеживаемого основания. Конфигуратор теперь запрашивает документ, редакцию и область применения каждого используемого значения и сбрасывает унаследованный источник при перезаписи числа.
- В описании каталога `BLOCKER` одновременно описывал тяжесть и подтверждённость нарушения. Теперь тяжесть отделена от статуса. План ревью и [пример отчёта о проверке](examples/review-result.example.json) имеют разное назначение.
- Инструкции установки обновлены под CLI, а команда `validate` проверяет схемы, наследование, ID и ссылки каталога.
- Добавлены матрица по объектам и режимам и проверка связей между критериями и доказательствами. В [учебном релейном сценарии](examples/relay-review/profile.yaml) две пары доменов и отдельные строки для clearance и creepage.
- Готовый KiCad DRC JSON можно импортировать с привязкой к объектам по UUID. Синтетический сценарий сохраняет активное замечание при коде завершения 0 и помечает исключение отдельно.
- Реальный импорт проверен на QA-плате `multinetclasses_drc` в KiCad 10.0.8. Для сопоставления замечаний по ширине добавлено явное направление границы. [Прогон KiCad](examples/kicad-multinetclasses/README.md)
- Добавлен read-only инвентарь нативной PCB. Импорт с платой сопоставил все шесть объектов DRC на том же QA-примере, проверил SHA-256 и извлёк сети, слои и RefDes.
- Добавлена сверка назначения сетей по `RefDes` и номеру вывода. Проверена на трёх демонстрационных проектах KiCad 10.0.8. Тестовое изменение экспортированного нетлиста выявлено со статусом `FAIL`. [Прогон сверки](examples/kicad-netlist/README.md)
- Добавлено чтение физического стека из PCB. Проверены двухслойный и шестислойный примеры с явным стеком и QA-плата без него.
- Добавлена сверка стека с заданными допусками и документами изготовителя. На реальной демонстрационной PCB проверены совпадение, превышение границы и неполные данные с учебными листами.
- Добавлен локальный запуск ERC и DRC на временной копии. Проверены иерархическая схема, активные ошибки QA-платы и пять сохранённых исключений DRC в демонстрационном проекте CM5.
- Расширено сопоставление геометрии DRC. В отчёте CM5 связаны 59 активных записей. На демонстрационных PCB прочитаны PTH, NPTH и продолговатые отверстия.
- Добавлена сверка формы, размеров, положения и металлизации отверстий с критериями чертежа. На двух демонстрационных платах проверены круглый NPTH и повёрнутый продолговатый PTH с учебными критериями.
- Добавлена диагностика версий, флагов CLI и методов `pcbnew`. В KiCad 10.0.8 выполнен DRC с пересчётом зон на временной копии. [Матрица совместимости](references/rules-engine.md#совместимость-kicad)
- При отсутствии метода классификации меди вокруг NPTH адаптер сохраняет геометрию. Сверка сетей показывает затронутые выводы с UUID и статусом `REVIEW_REQUIRED`. Это проверено с отключённым методом на демонстрационной плате и на тестовой сверке нетлиста.
- Матрица задаёт зазор меди для конкретной пары классов и режима. Импорт KiCad DRC предлагает критерий пары при известном назначении двух сетей. [Пары классов сетей](references/rules-engine.md#пары-классов-сетей)
- Ширина отрезков и дуг читается напрямую из платы. На `multinetclasses_drc` подтверждены два превышения максимума из правила QA-проекта по тем же UUID, что и в нативном DRC. [Сверка ширины дорожек](references/rules-engine.md#сверка-ширины-дорожек)
- GitHub Actions проверяет схемы, каталог, профили, учебный отчёт и тесты на Python 3.10 и 3.14. [Конфигурация CI](.github/workflows/validate.yml)
- В учебном отчёте артефакт DRC привязан по ID и SHA-256. При валидации проверяются байты файла и запись, указанная в замечании. [Целостность артефактов](references/rules-engine.md#целостность-артефактов)
- Инженерное исключение привязывается к подтверждённому `FAIL`. Валидация проверяет срок, ревизию и запрет исключений для правил электробезопасности. [Инженерные исключения](references/rules-engine.md#инженерные-исключения)
- При численном расхождении источников матрица требует обоснование выбора, владельца, дату и актуальную ревизию. Неподтверждённый критерий блокирует подтверждение результата. [Формат записи](references/rules-engine.md#подтверждение-и-расхождения-источников)
- Экспорт проверенного инженерного отчёта сохраняет отдельные поля статуса, тяжести, приоритета и уверенности. SARIF использует стабильные ID правил и ссылки на артефакты доказательств. [Команда экспорта](references/rules-engine.md#экспорт-инженерного-отчёта)
- Добавлена сверка прямых дорожек с замкнутым линейным `Edge.Cuts`. На `pic_programmer` измерено 3,56 мм для одной дорожки при минимуме проекта 0,01 мм. В тестах проверены вырезы, пересечения и открытый контур. [Охват сверки](references/rules-engine.md#сверка-зазора-меди-до-края)
- Добавлена численная сверка зазора выбранных пар прямых дорожек. В `pic_programmer` между `Net-(D4-A)` и `VCC` на `F.Cu` измерено 0,62 мм при минимуме 0,28 мм из настроек демонстрационного проекта. [Охват сверки](references/rules-engine.md#сверка-зазора-между-дорожками)
- Режим `--all-pairs` подбирает пары из UUID контекста по данным платы. Для `pic_programmer` из четырёх дорожек выбраны две пары на `F.Cu` с зазором 0,62 мм каждая. UUID, которые команда не смогла сопоставить с прямой дорожкой, выводятся отдельно и блокируют общий `PASS`. [Подбор пар](references/rules-engine.md#автоматический-подбор-пар)

## Приоритеты развития

| Приоритет работ | Наблюдение | Дополнение и критерий готовности |
|---|---|---|
| P0 | Матрица различает пары доменов и режимы, хранит подтверждение критерия и учитывает расхождения источников. В учебном сценарии изоляционные расстояния остаются неопределёнными. | Заполнить матрицу для открытого примера по источникам, согласованным ответственным инженером. |
| P0 | [Отчёт](schemas/report.schema.json) поддерживает проверку SHA-256 и указателей на записи для локальных JSON-артефактов. | Зафиксировать происхождение каждого артефакта, ревизию исходных файлов и применимость записи к охвату инженерной проверки. |
| P1 | [Каталог](rules/catalog.yaml) содержит преимущественно формулировки действий и ссылки на общие разделы. Часть правил использует базовую применимость и общий механизм семейства. | Уточнить предикаты, механизмы и доказательства на учебных платах. Начать с реле и защиты, DC/DC и возвратных токов, PHY/PoE и FPGA I/O. Проверить случаи с неизвестным, присутствующим и явно отсутствующим признаком. |
| P1 | Нативные прогоны выполнены с KiCad 10.0.8. Для 8.0 и 9.0 сверены руководства и API. Стек и отверстия сверены с учебными критериями. | Выполнить нативные прогоны на KiCad 8.0 и 9.0. Проверить сверку с согласованным листом изготовителя и чертежом. |
| P1 | [Список стандартов](references/standards-applicability.md) даёт документы-кандидаты. В профилях нет утверждённых требований конкретного изделия. | Согласовать один открытый эталонный профиль с ответственным инженером. Зафиксировать применимость, редакции, критерии и подписанта. Для EMC вести отдельные матрицы эмиссии и устойчивости. |
| P2 | В [списке задач](TASKS.md) остаются проверка клиентами и правила распространения. | Прогнать локальную установку в целевых версиях Codex и Claude Code, определить лицензию и порядок версионирования каталога. |

Следующие учебные сценарии могут дополнить релейный пример высокоскоростным каналом и моделью импульсного питания. Для каждого нужны входные файлы, ожидаемые ID и статусы, а также причина каждого исключения. В оценке ПЭМИН достаточно зафиксировать разрешённую область, ответственность и необходимость отдельной процедуры. Испытания и подтверждение безопасности остаются задачами компетентных специалистов.
