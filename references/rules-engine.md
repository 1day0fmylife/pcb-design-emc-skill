# Регламент AI/EDA проверки

## Входные данные

Минимально: revision schematic/PCB/BOM, EDA + версия, library hashes, stackup, fab capabilities, источники constraints с датами, power tree, интерфейсы и edge rates, механика, условия эксплуатации, safety/EMC цели. Проблемы с отсутствующими файлами пометить TBD. Скриншот не заменяет нативную плату.

## Алгоритм

1. Определить scope, разрешения на изменение файлов, выбранный `profiles/*.yaml`, проектные исключения и sign-off policy.
2. Проверить применимость каждого `rules/catalog.yaml` пункта; не делать вывод по имени net без знания физического назначения.
3. Извлечь контракт: criteria source, режим, численный предел с единицами, источник с ревизией, возможные погрешности и допуски.
4. Запустить штатные ERC/DRC только доступной и подтверждённой версии; не утверждать завершение без exit code и анализа report. При геометрическом анализе учесть zone fill и native design rules.
5. Для неавтоматизируемых правил провести review схемы, placement и пути возвратных токов. Для EMI использовать цепочку «источник → путь → приёмник» и альтернативные гипотезы.
6. Для расчётов SI/PI/thermal указать corner, модель, единицы и границы применимости; моделирование не равно измерению. Для EMC/ESD/surge предусмотреть испытания ответственного специалиста.
7. Каждому правилу присвоить `PASS`, `FAIL`, `REVIEW_REQUIRED`, `NOT_EVALUATED` или `N_A`; PASS только с положительным evidence относительно подтверждённого критерия.
8. Отсортировать findings по safety / влияние / достоверность; приоритет не должен подменять уверенность. Не автоприменять правки без разрешения и ревью.

## Конфигуратор профиля

[CLI](../scripts/pcb_profile.py) принимает ID стартового профиля либо путь к YAML/JSON. Он формирует план, по которому инженер собирает и проверяет доказательства. Правила и базовые семейства описаны в [каталоге](../rules/catalog.yaml) и [политике отбора](../rules/profile-checks.yaml).

- `feature_tags` перечисляет присутствующие признаки, `absent_feature_tags` — признаки, отсутствие которых установлено для этой конфигурации. Все остальные признаки неизвестны. Например, `low-voltage` не исключает наличие опасного напряжения в другом домене платы. Стартовый `surge-eft-esd` ставит вопрос о применимости в план, а программу и уровни испытаний определяет проект.
- `inherits` задаёт один родительский ID. CLI ищет одноимённый файл рядом с дочерним профилем, затем в `profiles/`. Изменения признаков и отдельных полей накладываются от родителя к потомку. Отсутствующее поле сохраняет наследованное значение, явный `null` сбрасывает его. Признаки могут подразумевать другие признаки согласно политике. Противоречия, повторяющиеся ключи и циклы наследования считаются ошибками ввода.
- `design_revision` указывает ревизию конкретной платы. Значение `approved` относится к текущему профилю и передаётся в JSON как декларация.
- `inputs` хранит локаторы документов, например `stackup: "FAB-STACKUP, rev C, таблица 2"`. CLI фиксирует наличие локатора. Доступность, актуальность и содержание документа проверяет инженер.
- `constraints` хранит числа в единицах из имён полей. Для принятия числа в план укажите одноимённый элемент `constraint_sources` с `document`, `revision` и `scope`. При изменении или повторном задании числа укажите его источник в том же файле. Если источник пропущен, отчёт запрашивает его заново.
- Числа профиля описывают конкретную область. `min_copper_gap_mm` относится к заданной геометрии, `controlled_impedance_ohm` — к указанному каналу, `max_current_a` — к указанной ветви и режиму. Критерии для отдельных объектов задаются в матрице. Для изоляционных расстояний нужны самостоятельные критерии ответственного инженера.

Пример заполнения части профиля ссылками на документы.

```yaml
design_revision: "HW-C"
feature_tags: [relay, external-ports]
absent_feature_tags: []
inputs:
  schematic: "CTRL-SCH, rev C"
  relay_coil: "CTRL-RELAYS, rev C, раздел Катушка"
  relay_contacts: "CTRL-RELAYS, rev C, раздел Нагрузка контактов"
  insulation_matrix: null
```

Каждая строка `when` в политике — набор обязательных признаков, а несколько строк задают альтернативы. Правило отбирается, если выполнена хотя бы одна строка. При явном исключении хотя бы одного признака из каждой строки план выдаёт `N_A` с основанием профиля. Если остаётся незакрытая альтернатива, план выдаёт `REVIEW_REQUIRED`. Правило без условия входит в базовый скрининг. Инженер уточняет его применимость к объектам платы.

Выбранные правила получают `REVIEW_REQUIRED` при нехватке входов или источников и `NOT_EVALUATED` при их наличии. Если ревизия платы не задана, её нужно уточнить на уровне плана. В Markdown выбранные правила сгруппированы по назначению, а неопределённые и исключённые собраны по условиям. JSON `report_type: profile_review_plan` включает версии каталога и политики отбора, все правила, исходные данные, ограничения, основания применимости и список связанных с каждым пробелом ID. Он предназначен для подготовки ревью. Результаты реальной проверки оформляются по [схеме отчёта](../schemas/report.schema.json). Открытые вопросы ПЭМИН вынесены в отдельную область без критериев соответствия.

## Report/waiver contract

Каждая находка: rule ID, scope, RefDes/net/layer/coordinates при наличии, criterion, revision, evidence, severity, confidence, mechanism, recommendation, verification method, limitations, status. Waiver хранит owner, причину, дату и пересмотр; не разрешает несоответствие обязательному safety стандарту.

### Матрица критериев

В `review_objects` задайте стабильный ID объекта, `kind` и список `modes`. У `domain_pair` поле `members` содержит ID двух доменов. В `criteria` задайте стабильный ID критерия, `object_id`, `rule_id`, `mode`, `metric`, `unit`, `limit` и `source` с полями `document`, `revision`, `section`. Для импеданса укажите также абсолютный `tolerance` в омах.

| Объект | Метрика | Правило | Сравнение |
|---|---|---|---|
| `domain_pair` | `clearance`, `creepage` | `PCB-GEO-002` | Минимум в мм для каждой метрики |
| `net_class` | `copper_gap` | `PCB-GEO-001` или `PCB-DFM-001` | Минимум в мм |
| `board` | `copper_to_edge` | `PCB-GEO-003` | Минимальный зазор меди до `Edge.Cuts` в мм |
| `net_class` | `trace_width` | `PCB-DFM-001` | Минимум в мм |
| `net_class` | `trace_width_max` | `PCB-DFM-001` | Максимум в мм |
| `port` | `controlled_impedance` | `PCB-HS-001` | Целевое значение и допуск в омах |
| Любой объект, включая `component` и `board` | `qualitative` | Применимое правило из каталога | Проверяемое условие `requirement` |

Для `qualitative` укажите `requirement` и источник условия. Числовые поля нужны для количественных метрик.

Матрица относится к текущей ревизии платы и берётся из конечного профиля. Общие признаки и ограничения по-прежнему наследуются. Объявление пары доменов включает проверку изоляции. План подставляет строки для отсутствующих `clearance` и `creepage` в каждом режиме пары. Если значение, допуск или источник отсутствуют, строка получает `REVIEW_REQUIRED`. При наличии входных данных требуется отдельная проверка, поэтому план оставляет `NOT_EVALUATED`.

### Проверка результата

`validate-report PROFILE REPORT` сверяет инженерный JSON со схемой, ID профиля и ревизией платы. Для `PASS` или `FAIL` укажите `criterion_id`, `object_id`, метод `verification` и `evidence_ref` с `artifact` и `locator`. Для численного критерия добавьте `measurement` с числом и единицей, для качественного — `assessment` со значением `satisfied` или `not_satisfied`. CLI проверяет согласованность статуса с результатом. Критерий, метод и артефакт подтверждает инженер.

Общий `PASS` относится к явному `scope_criteria` и требует результата `PASS` для каждого ID в заявленном охвате. Если общий отчёт включает хотя бы один подтверждённый `FAIL`, его итоговый статус — `FAIL`. Для общей готовности изделия требуется отдельно установить полный охват ревью.

## KiCad

Для штатного запуска ERC/DRC сверяйте версию и `--help` локального `kicad-cli`. Команда `import-drc` читает готовый JSON v1. Она сохраняет три раздела, типы замечаний, текст, координаты, единицы и исключения. Результат сохраняет ссылки на позиции в исходном артефакте. [Схема DRC KiCad](https://schemas.kicad.org/drc.v1.json)

### Локальный запуск ERC и DRC

```sh
python3 scripts/pcb_profile.py run-checks --schematic path/to/project.kicad_sch \
  --board path/to/project.kicad_pcb --design-revision REVISION \
  --output-dir path/to/new-report-directory
```

Для ERC укажите корневой лист. Можно запустить одну проверку, передав только схему или только плату. По умолчанию используется каталог входного файла. Если входы или относительные зависимости лежат в разных каталогах, задайте общий `--project-dir`. Работа ведётся во временной копии CAD-файлов, таблиц и локальных библиотек внутри этого корня. Пропущенные при копировании пути перечисляются в сводке. Глобальные таблицы библиотек и настройки путей копируются из локальной установки. При отсутствии пользовательских таблиц используются доступные штатные таблицы шаблона KiCad. [Конфигурация KiCad](https://docs.kicad.org/10.0/en/kicad/kicad.html)

Команда проверяет версию и наличие нужных параметров в `--help`. Для каждого запуска сохраняются исходный `erc.json` или `drc.json`, stdout, stderr и код завершения. Тайм-аут на отдельный вызов задаёт `--timeout`. DRC по умолчанию использует сохранённые заливки. `--refill-zones` пересчитывает заливки в памяти временной копии при наличии поддержки в KiCad. Исходные файлы сверяются по SHA-256. [KiCad CLI 10.0](https://docs.kicad.org/10.0/en/cli/cli.html) · [Схема ERC v1](../schemas/kicad-erc.schema.json)

В `summary.json` ошибки, предупреждения и исключения учитываются отдельно. При подтверждённой ревизии и настройках проекта активные ошибки дают `FAIL`, в том числе при коде KiCad `0`. Предупреждения, исключения, отключённые проверки и недостающие данные дают `REVIEW_REQUIRED`. Чистый результат получает `PASS` в пределах запрошенной проверки при подтверждённом охвате. Состояние отсутствующей или несовместимой CLI фиксируется как `NOT_EVALUATED`. Для автоматизации используйте `overall_status` из JSON. Код возврата оболочки `run-checks` отражает формирование сводки, а коды KiCad хранятся внутри неё.

Проверено с KiCad 10.0.8. В проекте `pic_programmer` обработаны два листа ERC и DRC с пересчётом заливок. На QA-плате `multinetclasses_drc` подтверждены две ошибки. В DRC демонстрационной платы `CM5_MINIMA_3` сохранены пять исключений.

### Импорт готового DRC

В `--context` укажите `design_revision` из профиля и `board_source` как в поле `source` отчёта. При наличии приложите код завершения `exit_code`, режим `mode` и таблицу `items` по UUID в нижнем регистре. Для каждого UUID укажите известные `refdes`, `net`, `layer` и `object_id`. Эти данные сверяются с ревизией платы до импорта. [Схема контекста](../schemas/kicad-context.schema.json)

Привязка к критерию требует общего объекта у всех элементов замечания. Для `track_width` сначала сверьте правило KiCad и укажите `min` или `max` в `track_width_bounds` по позиции вида `/violations/0` из того же отчёта. При пропуске направления импорт оставляет кандидат правила без привязки к критерию. Если режим не указан и подходят несколько критериев, импорт показывает их все. Замечания импорта имеют `REVIEW_REQUIRED`. Пустой отчёт получает `NOT_EVALUATED`, а наличие замечаний определяется содержимым файла, включая случаи с кодом завершения 0.

### Сопоставление геометрии DRC

| Тип замечания KiCad | Кандидат правила | Уточнение |
|---|---|---|
| `clearance` | `PCB-GEO-001` | Зазор меди для указанного класса сетей |
| `copper_edge_clearance`, `copper_outside_board` | `PCB-GEO-003` | Геометрия меди у контура |
| `annular_width` | `PCB-GEO-005` | Ширина кольца, направление ограничения проверяется по проекту |
| `hole_clearance` | `PCB-GEO-006` | Зазор меди до отверстия |
| `hole_to_hole`, `holes_co_located`, `drill_out_of_range`, `microvia_drill_out_of_range`, `via_diameter` | `PCB-DFM-001` | Геометрия отверстий по технологии изготовителя |
| `solder_mask_bridge` | `PCB-DFM-003` | Перемычки паяльной маски |
| `isolated_copper` | `PCB-GND-003` | Изолированный участок заливки |
| `track_width` | `PCB-DFM-001` | Ширина дорожки с явно указанным минимумом или максимумом |

Для `copper_edge_clearance` привязка к численному критерию `copper_to_edge` требует установленного `Edge.Cuts` у вовлечённого объекта и общей привязки к объекту `board` в контексте. Объекты на `Margin` требуют отдельной проверки применимости. Остальные геометрические типы без указанной метрики дают только кандидата правила. `active_candidates_by_rule` считает активные записи DRC, включая записи об одних и тех же объектах. Критерии изоляции и `creepage` проверяются по матрице пар доменов.

На CM5 с KiCad 10.0.8 сопоставились 59 активных записей, в том числе два замечания по меди до края. В исходном отчёте сохранены все 176 записей с пятью исключениями. [Типы DRC KiCad](https://docs.kicad.org/doxygen/drc__item_8cpp_source.html) · [Проверка края и Margin](https://docs.kicad.org/doxygen/drc__test__provider__edge__clearance_8cpp_source.html)

### Чтение платы по UUID

`inventory-board BOARD` читает `.kicad_pcb` через установленный `pcbnew`. Проверена версия 10.0.8. JSON содержит SHA-256 платы, версию формата, слои, сети и инвентарь объектов по UUID. Охвачены посадочные места, площадки, поля и графика, дорожки, переходные отверстия и зоны. Для площадок сохраняются номер, RefDes и UUID посадочного места. Для площадок с отверстием добавляются тип PTH или NPTH, форма и размеры в локальных осях площадки в мм. [API KiCad 10.0](https://docs.kicad.org/doxygen-python-10.0/classpcbnew_1_1PCB__IO__KICAD__SEXPR-members.html)

При `import-drc --board BOARD` используется файл с тем же именем, что в `source` DRC. Если в контексте задан `board_sha256`, он должен совпасть с файлом. Для каждого элемента выводятся результат сопоставления и сведения из платы. У многослойных объектов сохраняется список слоёв. Импорт сверяет поля `refdes`, `net` и `layer` из ручного контекста с доступными сведениями платы. `object_id` и направление границы ширины по-прежнему задаются в контексте. Если UUID отсутствует в инвентаре, замечание сохраняется с `not_found`, а привязка к критерию требует ручной проверки.

### Сверка схемы и платы по нетлисту

Для `PCB-CONN-001` экспортируйте XML-нетлист корневой схемы командой `kicad-cli sch export netlist --format kicadxml`. Экспорт формирует назначения сетей с учётом иерархии листов. Если проект использует варианты, явно выберите нужный вариант и зафиксируйте его вместе с ревизией входов. Передайте экспорт, исходную PCB и общую ревизию в `compare-netlist --board BOARD --netlist XML --design-revision REVISION`. В отчёт попадают пути и SHA-256 обоих файлов. [Документация KiCad CLI](https://docs.kicad.org/10.0/en/cli/cli.html#schematic-export-netlist)

Критерий сверки — совпадение состава сравниваемых компонентов и назначения сетей по `RefDes` и номеру электрического вывода. KiCad раскрывает экранирование полного имени сети PCB перед сравнением с XML. Для явно помеченного в экспорте `no_connect` допустима площадка без сети или с совпадающим именем. Механические площадки без меди и посадочные места с флагом `Board only` исключаются из этой сверки. Для остальных исключений требуется отдельное обоснование по проекту.

Отчёт `kicad_netlist_comparison` указывает `PASS` для согласованных назначений в заявленном охвате. При пропущенном обязательном входе, неоднозначном сопоставлении или неопределённом имени сети используется `REVIEW_REQUIRED`. Подтверждённое расхождение получает `FAIL` с ожидаемой сетью и UUID площадки, если она есть. Физическую целостность трасс и электрические правила проверяют DRC и ERC.

### Физический стек платы

```sh
python3 scripts/pcb_profile.py inventory-stackup path/to/board.kicad_pcb --output stackup.json
```

Команда использует `pcbnew` для порядка медных слоёв и читает явно сохранённые свойства из `setup/stackup`. JSON содержит SHA-256 платы, слои и подслои, толщины в мм, материалы, `epsilon_r`, `loss_tangent` и опции покрытия при наличии. `declared_board_thickness_mm` берётся из `general/thickness`. `declared_stack_thickness_mm` суммирует слои меди, диэлектрики и маску, перечисленные в стеке, при полном наборе толщин и согласованном порядке слоёв. [Формат KiCad PCB](https://dev-docs.kicad.org/en/file-formats/sexpr-pcb/)

Если секция стека отсутствует, JSON сохраняет порядок медных слоёв и явно записанную толщину платы. У такого случая статус `REVIEW_REQUIRED` и пустой список слоёв физического стека. Недостающие поля и расхождения в порядке слоёв перечисляются в `issues`. Полный экспорт получает `NOT_EVALUATED` до сверки со стеком изготовителя. Номиналы из CAD используются как исходные данные для `PCB-DFM-002` и `PCB-HS-001` после проверки источника.

### Сверка стека с изготовителем

```sh
python3 scripts/pcb_profile.py compare-stackup --board path/to/board.kicad_pcb \
  --fabrication path/to/fabrication-stackup.yaml --design-revision REVISION \
  --output stackup-comparison.json
```

В YAML или JSON перенесите из согласованного листа изготовителя `design_revision` и `source` с полями `manufacturer`, `document`, `revision` и `section`. Необязательный `board_sha256` позволяет привязать лист к точному файлу PCB. В `total_thickness.basis` укажите `board` для номинала платы из `general/thickness` или `stack` для суммы явно сохранённых слоёв. Выберите то же определение толщины, что использовано в документе изготовителя. [Схема](../schemas/fabrication-stackup.schema.json)

В `layers` указывайте слои сверху вниз под их именами в KiCad. Для каждого укажите подслои в физическом порядке. Толщины задаются в мм через включительные `min` и `max`. Для меди сверяйте толщины на одной и той же стадии процесса, указанной в документе. Для односторонней границы достаточно одного поля. При наличии согласованного критерия добавьте точное имя `type`, `material` или `copper_finish` на соответствующем уровне. Паяльная маска сравнивается по слоям, если они включены в документ. Для полноты базовой сверки нужны общая толщина и границы по слоям меди и диэлектрика.

Свойства `epsilon_r` и `loss_tangent` сравниваются при совпадении `spec_frequency_hz` из листа и явно сохранённой частоты в PCB. Сопоставимость материала, метода измерения и условий подтверждает инженер. Если частота неизвестна или отличается, эта проверка получает `REVIEW_REQUIRED`. [Единицы частоты KiCad](https://docs.kicad.org/doxygen/classDIELECTRIC__PRMS.html)

При неизвестной ревизии, несовпадении контрольной суммы или неполном источнике результат остаётся `REVIEW_REQUIRED`. При подтверждённой привязке каждая проверка получает собственный статус, а любое установленное расхождение даёт итоговый `FAIL`. `PASS` относится к сравнению CAD с явно заданными критериями. Фактические параметры выпущенной платы подтверждаются изготовителем.
